# 可追踪验收闭环

先读 `internal/develop/traceable-acceptance.md`（方法论），再看当前阶段的执行计划。

## 何时使用

- 一个阶段声称完成，需要判断能否验收
- 行为可疑或结果不稳定，需要定位是哪一层出了问题
- 修完一个缺陷，需要决定把它沉淀成什么资产

## 循环

1. **锁定阶段。** 写清主线目标、当前阶段、本轮只做什么、明确禁止什么、退出条件。design 和 acceptance 阶段不顺手改代码。
2. **写清验收对象。** 以用户目标表达，不以内部模块表达。
3. **画出主链。** 把从用户输入到可见结果的路径写成节点序列，标出每个节点的 current owner。
4. **证据合同。** 每个节点写明可观测证据、通过判据、失败分类。没有证据列的节点不得出现在"已通过"里。
5. **跑真实路径。** 优先真实 CLI 进程；其次是录制夹具驱动的集成测试；单元测试只作补充。"应该""理论上""看起来"都不是证据。
6. **给出分级结论。** Pass、Partial、Evidence Gap、Fail 之一，写到具体节点。
7. **沉淀回归。** 每个 Partial、Evidence Gap、Fail 都要转成一种后续资产：测试、夹具、冒烟场景、守卫、执行计划条目或治理规则。

## 失败分类

spec_gap、context_gap、routing_gap、protocol_gap、mock_leakage、persistence_gap、projection_gap、evidence_gap、eval_gap、policy_gap，以及环境噪音。含义见方法论的失败分类一节。不要把环境噪音或夹具缺口误报为产品通过。

## 输出

- 结论级别
- 已证实节点与证据位置
- 未证实节点
- 失败分类
- 沉淀的后续资产
- 完成度百分比
