# 可追踪验收方法论

> 状态：current
> 参考来源：lime 仓库 internal/develop/traceable-agent-acceptance-methodology.md 的方法骨架，按 lime-star 的主链与术语改写。
> 本页只定义方法，不替代根 AGENTS.md、`../aiprompts/architecture.md` 和 `../aiprompts/quality-workflow.md`。

## 这份文档回答什么

自动检查通过，不等于用户目标真的跑通。本页定义 lime-star 判断"一条用户路径是否真的成立"的统一做法：每个关键节点有没有可关联的证据，失败时能不能定位到明确的卡点。这套做法称为**可追踪验收闭环**。

它吸收了四类工程实践，但全部落回 lime-star 自己的主链：先定规格再实现；把上下文当作可靠性的输入；把模型调用和工具调用做成可观测事实；把验收结果沉淀成评测。

## 什么时候用

- 一个阶段声称完成，需要判断能否验收
- 行为不稳定或结果可疑，需要定位是哪一层出了问题
- 修完一个缺陷，需要决定把它沉淀成什么资产

只改文案、只做只读调查，或改动不经过 app 回合入口时不需要。

## 核心原则

### 证据优先于叙述

Agent 不能只说"应该写入了""理论上注入了""看起来成功了"。可接受的证据只能来自真实事实源：

- transcript 里的 item 记录
- app 回合入口的 thread 读取结果
- 请求日志里带关联键的记录
- 真实 CLI 进程的终端输出
- 证据导出包
- 测试里完整的断言对象

没有证据的节点不必立刻判失败，但必须判为**黑盒断点**，不能写进"已通过"。

### 主链优先于局部成功

用户路径必须经过 app 回合入口。只跑了单元测试、只证明内存里有数据、只证明某个函数返回值正确，都只能声明对应局部通过，不能声明用户目标通过。

### 验收链不替代测试

验收链回答"这次真实路径是否清楚"，测试回答"以后会不会回归"。验收链发现的缺口，要沉淀回测试、夹具、守卫或执行计划。

| 层级 | 主要问题 | 入口 |
| --- | --- | --- |
| 单元与集成测试 | 局部逻辑与模块协作是否正确 | `uv run pytest` |
| 契约检查 | schema 与消费者是否一致 | `npm run test:contracts` |
| Current fixture | 主链接线是否正确 | 录制夹具驱动的集成测试 |
| Gate B 冒烟 | 真实进程端到端是否成立 | scripts/smoke/ 下的冒烟脚本（路线图 P4 起） |
| 可追踪验收链 | 关键节点是否可解释、可定位、可复盘 | 证据导出、transcript、人工裁决 |

### 先限定阶段，再动手

- design：只建模链路、证据和判据，不改代码。
- goal：按已确认的设计实施最小闭环。
- acceptance：只跑验收链并给出结论，不顺手改代码。
- regression：把发现的缺口沉淀成测试、评测或守卫。

在 acceptance 阶段顺手改代码，或在 design 阶段顺手扩大治理清理，都算目标漂移。

## 统一模型：一次验收看五条链

1. **目标链**：用户目标、成功行为、可见结果、不做范围、风险边界。
2. **上下文链**：本轮给了模型什么上下文，来源是否可信，能否证明它进入了请求。
3. **运行链**：请求如何穿过主链：CLI 输入、app 回合入口、agent_runtime、model_provider 与 tool_runtime、thread_store、终端投影。
4. **证据链**：凭什么说它发生了。证据只能从 transcript 和请求日志导出，不能由终端显示反推。
5. **回归链**：这次结论如何变成下次不靠记忆的资产：定向测试、夹具、冒烟场景、守卫、执行计划条目。

## 标准流程

### 1. 锁定阶段

用 3 到 8 行写清主线目标、当前阶段、本轮只做什么、明确禁止什么、退出条件。

### 2. 写清验收对象

以用户目标表达，不以内部模块表达。示例：

```text
作为用户，我希望：当我拒绝一次危险操作后，Agent 不执行它，并在 transcript 里留下被拒绝的记录，
这样我能确认审批是真的生效，而不是只弹了一个提示。
```

### 3. 画出主链

写成节点序列，不要先写大段解释，并标出每个节点的 current owner。

### 4. 证据合同

每个节点一行，五列。没有证据列的节点，不得出现在"已通过"里。

| 节点 | current owner | 可观测证据 | 通过判据 | 失败分类 |
| --- | --- | --- | --- | --- |
| （示例）工具调用 | tool_runtime | transcript 里的工具调用与结果 item | 调用与结果成对出现，顺序正确 | protocol_gap |

### 5. 跑真实路径

验收优先级：真实 CLI 进程；录制夹具驱动的集成测试；单元测试作补充。以下不能作为主验收通过：生产路径用了替身；Agent 自报完成；只看终端截图不看事实源；只看内存状态不看 transcript。

### 6. 给出分级结论

| 级别 | 含义 |
| --- | --- |
| Pass | 用户目标主链的每个节点都有证据 |
| Partial | 局部通过，主链仍有断点 |
| Evidence Gap | 功能可能存在，但缺可观测证据，不能宣称通过 |
| Fail | 已有证据证明行为错误 |

结论必须写到具体节点，禁止"基本通过""看起来没问题"。

### 7. 沉淀回归资产

每个 Partial、Evidence Gap、Fail 都要转成一种后续资产：

| 缺口 | 后续资产 |
| --- | --- |
| 规格不清 | 更新路线图或阶段计划 |
| owner 不清 | 更新 governance.md 或 architecture.md |
| 契约不一致 | 契约检查或契约测试 |
| 事实源内容不对 | 入口集成测试或 Gate A 断言 |
| 终端显示与事实源不一致 | 冒烟场景 |
| 模型行为不稳定 | 录制夹具或评测样本 |
| 证据无法关联 | 请求日志关联键或证据导出的修正任务 |

如果一次验收发现了黑盒断点，却没有产生任何可追踪的后续资产，这次验收只算一次人工观察，不算闭环。

## 失败分类

- spec_gap：目标、范围或验收标准不清。
- context_gap：上下文来源、预算或裁剪不清。
- routing_gap：模型、工具或回合入口的路由错误。
- protocol_gap：类型、schema 与消费者不一致。
- mock_leakage：生产路径误用了替身或回放而没有标注。
- persistence_gap：transcript 或读模型缺失、不一致。
- projection_gap：事实源里有，但终端没有正确显示。
- evidence_gap：功能可能发生，但缺少可关联证据。
- eval_gap：没有把行为沉淀成可重复的评测或夹具。
- policy_gap：审批、路径边界或敏感信息边界不清。
- 环境噪音：与产品行为无关的本机或网络问题。

## 给 Agent 的提示模板

进入设计阶段：

```text
进入 lime-star 可追踪验收的设计阶段。只做方法建模，不改代码、不新增测试。
请输出：
1. 用户目标
2. 主链路节点
3. 每个节点的 current owner
4. 每个节点需要的可观测证据
5. 通过判据与失败分类
6. 黑盒断点
7. 下一步最小验收动作
"应该""理论上""看起来""可能"不能作为通过证据。
```

进入验收阶段：

```text
进入 lime-star 的验收阶段。只判断，不改代码。
基于真实路径判断；不用替身、回放、Agent 自报或单纯截图替代证据。
输出：
- Pass / Partial / Evidence Gap / Fail
- 已证实节点与证据位置
- 未证实节点
- 失败分类
- 下一刀应沉淀成测试、夹具、守卫、执行计划还是治理规则
```

进入复盘阶段：

```text
进入验收复盘。把本次的黑盒断点转成可维护资产：
1. 哪些进入自动化测试
2. 哪些进入夹具或评测样本
3. 哪些进入证据导出或请求日志关联键的修正
4. 哪些进入治理规则
5. 哪些只是人工验收备注，不应扩大成主线任务
```

## 反模式

- 只看终端输出，不看 transcript。
- 只看内存状态，就宣称用户目标通过。
- 用回放夹具的结果冒充真实模型通过。
- 没有关联键，却声称有请求级证据。
- 把一次验收结论留在聊天里，没有转成任何后续资产。
- 在 acceptance 阶段顺手改代码，或在 design 阶段顺手扩大治理清理。
- 为了让链路看起来完整，输出不存在的记录或测试结果。
