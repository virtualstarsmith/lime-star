# Lime 开发范式学习使用手册

> 本手册提炼自 lime 仓库（一个 Electron + Rust 的 AI Agent 产品）的实际治理方式。它不是理论框架，而是一套已在多人多 Agent 长期协作中运转的工程制度。读完本手册，你可以把这套范式搬进任何项目。
>
> 本手册提炼自 lime 仓库，是范式的学习材料，不定义本仓库规则。配套文件已落在本仓库；日常速查见 paradigm-quick-checklist.md，实际落地记录见 internal/exec-plans/。

---

## 1. 这套范式解决什么问题

当开发变成"人 + 多个 AI Agent 长期协作"，工程失控主要表现为四种病：

| 病 | 表现 | 范式的药方 |
| --- | --- | --- |
| **双轨并存** | 新旧两套实现同时活着，没人敢删旧的，compat 层越积越厚 | 四态生命周期 + 直接替换原则（`3.2） |
| **规则不落地** | 规范写在文档里，Agent 看不到、看到了也不执行 | 事实源分层 + 每条规则配机械守卫（`3.1、`3.4） |
| **证据造假** | 单测通过就说"功能完成"，用弱证据冒充强证据 | 证据分级 Gate A/B + 验证记录纪律（`3.5） |
| **并行互踩** | 多个 Agent 同时改一个仓库，互相覆盖对方改动 | 窄写集认领 + 脏热区避让（`3.6） |

一句话概括这套范式：**让"事实源"分层可见，让每条规则变成可执行的命令，让每轮改动带着写集进、带着证据出。**

## 2. 全景图

```
                 ┌─────────────────────────────────────────┐
                 │  AGENTS.md（仓库级约束 + 导航，唯一的"根"）      │
                 └───────────────┬─────────────────────────┘
                                 │ 指向
        ┌────────────────────────┼───────────────────────────┐
        ▼                        ▼                           ▼
┌──────────────────┐  ┌──────────────────────┐  ┌──────────────────────────┐
│ internal/        │  │ internal/exec-plans/ │  │ scripts/ + governance/   │
│ aiprompts/       │  │ 执行计划：目标/写集/    │  │ 机械守卫：行数棘轮、冻结    │
│ 领域规则：架构、   │  │ 退出条件/验证/阻塞；    │  │ 基线、契约同步；           │
│ 治理、质量、并行   │  │ 进度按"刀"追加；       │  │ verify:local 聚合成       │
│ 协作             │  │ 收尾四分类+完成度      │  │ 默认本地门禁              │
└────────┬─────────┘  └──────────┬───────────┘  └────────────┬─────────────┘
         │ 裁决                  │ 记录                       │ 执行
         ▼                      ▼                           ▼
   ┌─────────────────────────────────────────────────────────────┐
   │                     代码仓库（唯一记录系统）                      │
   │          每种能力只有一个 current owner；退役即物理删除           │
   └─────────────────────────────────────────────────────────────┘
```

信息流向：

- **规则从上往下**：AGENTS.md 定约束 → aiprompts 落领域规则 → scripts 变成命令；
- **事实从下往上**：代码和测试是最终裁决，规则与代码冲突时改规则；
- **执行横向走**：每个长任务在 exec-plans 里开计划，写集进、证据出、四分类收尾。

## 3. 七大机制详解

每节按固定结构讲：是什么 → Lime 里怎么做的 → 模板对应文件 → 在新项目怎么用。

### 3.1 事实源分层与导航

**是什么**：把"规则写在哪儿"变成一棵明确的树，任何 Agent 开工前都能在两跳内找到该读的规则。

**Lime 怎么做的**：

- 根 `AGENTS.md` 只有六节：事实源、工程约束、协议与质量、执行方式、导航、高频命令——它自己声明"根文件只保留仓库级约束和导航"；
- `internal/aiprompts/` 是领域规则层（40 个文档，每个单一主题），其中 `architecture.md` 是**唯一裁决源**，开头写明裁决顺序：`运行代码/稳定测试 → 架构图与 AGENTS.md → 领域文档 → 执行计划 → Git history`；
- `README.md` 只做场景路由（"改 X 前先读 Y"的两跳表），自己不定规则；
- 每个领域文档开头都有一句免责声明："目录、依赖方向以 architecture.md 为准，本页只定义……"——形成单向引用闭环，没有第二裁决源。

**模板对应**：`AGENTS.md`、`internal/aiprompts/README.md`、`internal/aiprompts/architecture.md`。

**新项目怎么用**：

1. 先写 AGENTS.md（半页到两页），只放"必须永远成立"的约束；
2. 建 `internal/aiprompts/`，第一批只放 architecture.md（裁决顺序 + 目录地图 + 主链）；
3. 领域文档按需增长，每个新文档必须回答："我的边界以谁为准？"并链接上去。

**何时可裁剪**：单人小项目可以只有 AGENTS.md 一个文件；只要开始有第二个 Agent 或第二套子系统，就立刻补 architecture.md。

### 3.2 四态生命周期治理

**是什么**：给"同一种能力的新旧实现并存"一个唯一的收敛语法。

**Lime 怎么做的**（governance.md 原文规则）：

> 同一种能力在同一时期只能有一个继续演进的 owner。先写清事实源，再动代码：
> - `current`：唯一产品路径，可以新增能力。
> - `compat`：只做边界适配和委托，不得新增业务逻辑。
> - `deprecated`：只允许迁出和删除。
> - `dead`：无入口或已被替代，删除并补回流守卫。

配套三条硬规则：

1. **直接替换原则**："发现重复实现、临时路径或已脱离构建图的代码，优先删除或直接替换，不保留双轨"，并且"不要为了降低 diff 新增新的 compat 层"；
2. **修改前四层盘点**：入口层 / 服务层 / 存储层 / 旁路层——若无法指出唯一 current owner，不扩展功能，先完成收敛；
3. **退役三件套**：物理删除 + 负向守卫（测试断言旧名不得回流）+ `dead / deleted / forbidden-to-restore` 措辞（精确到 method 名、枚举值、事件名）。

这套措辞在 Lime 的 architecture.md 里出现了约 50 次，覆盖每个退役对象。

**模板对应**：`internal/aiprompts/governance.md`。

**新项目怎么用**：

- 每次动手前先问："这个能力的 current owner 是谁？"答不出来就不写代码，先收敛；
- 删除能力时执行退役三件套，缺一不可——只删代码不补守卫，三个月后一定会被"恢复兼容"复活。

**何时可裁剪**：没有历史包袱的新项目可以把"直接替换原则"写成绝对式（模板默认如此）；有存量用户的项目必须先在 governance.md 声明豁免范围和退出条件。

### 3.3 执行计划体系

**是什么**：长任务不再活在聊天记录里，而是活在仓库里的一个 versioned 计划文件中。

**Lime 怎么做的**：

- `internal/exec-plans/` 下每个长任务一个 `<topic>-plan.md`，固定骨架：**目标 → 当前事实 → 写集与避让 → 删除集 → 阶段与退出条件 → 验证矩阵 → 架构确认 → 进度记录 → 当前结论**；
- 进度按"刀"追加（一"刀" = 一轮可验证的完整改动），每刀记录：改动、验证（含未跑原因）、完成度百分比、**下一刀**；
- 收尾必须输出**治理四分类**：current / compat / deprecated / dead 的增删清单、验证结果、未验证原因、完成度百分比；
- 没有归档目录：被替代且无兼容负担的计划**直接删除**，历史归 Git；删不动的长期残留挂 `tech-debt-tracker.md`（带编号和退出条件）。

Lime 计划文件里的典型进度记录（示范了"证据诚实"）：

> 定向回归 32 tests 通过。尚未把该单测结果冒充真实 Electron disconnect Gate B evidence。

**模板对应**：`internal/exec-plans/README.md`、`internal/exec-plans/templates/task-plan.md`、`internal/exec-plans/templates/agent-verification-contract.md`、`tech-debt-tracker.md`。

**新项目怎么用**：

- 判据：预计超过一轮对话、跨会话、或影响主链的任务 → 开计划；改个错别字不用；
- 开工时写前三节（目标/当前事实/写集），不用一次写全；
- 每收工一次就追加一刀，收尾写四分类。

**何时可裁剪**：进度日志（`<topic>-progress.md`）只在并行避让时需要；验证合同只在主链改动时需要。

### 3.4 规则工具化门禁

**是什么**：每条"必须/禁止"规则都对应一个可执行的检查命令，规则不靠自觉，靠退出码。

**Lime 怎么做的**：

| 硬规则 | 机械守卫 |
| --- | --- |
| 非生成文件 800 行预警 / 1000 行硬限 | `governance:file-size`（行数棘轮：基线文件只许收缩） |
| scripts 目录冻结基线 | `governance:scripts`（根文件与一级目录进基线，基线只许收缩） |
| 协议/契约变更必须同步消费者 | `test:contracts`（聚合多个契约检查） |
| 退役 surface 不得回流 | `governance:legacy-report`（扫描 import/命令/文案残留，有违规即失败） |
| 重大变更必须有架构确认 | `governance:architecture-confirmation`（只接受重大声明） |
| 用户可见文案覆盖 5 种语言 | `i18n:check` + `i18n:scan` |
| 以上全部 | `verify:local` 聚合成默认门禁，按 git diff 增量选任务 |

两个关键设计：

- **基线棘轮**：对存量违规不搞一刀切，而是把现状冻结成基线 JSON，规则是"只许变好不许变坏"（超线文件只许收缩，允许 ±5% 回弹）。这让门禁可以在有历史包袱的项目里落地——今天起不再恶化，存量逐步清退；
- **`--update` 是确认不是赦免**：跑 `--update` 表示"我确认当前状态是可接受的基线"，这是一个显式的、会进版本库的动作，而不是偷偷放宽。

**模板对应**：`scripts/` 下四个零依赖脚本 + `scripts/README.md`。

**新项目怎么用**：

1. 首日就接入 `verify:local` 编排器 + 行数棘轮（成本最低、收益最大）；
2. 每新增一条 AGENTS.md 硬规则，问自己："它的退出码在哪里？"答不出来就不要写这条规则；
3. 把守卫挂进 verify-local 的任务表（按路径前缀增量触发）。

**何时可裁剪**：契约检查在只有内部接口的项目里可以延后；legacy-report 等有退役需求时再写。

### 3.5 证据分级

**是什么**：给"验证过没有"一个统一的强度刻度，杜绝"单测过了 = 功能完成"式的证据造假。

**Lime 怎么做的**（quality-workflow.md 定义了从弱到强的等级）：

| 等级 | 能证明 | 不能证明 |
| --- | --- | --- |
| Unit | 局部逻辑正确 | 集成与真实链路 |
| Domain integration | 模块组装正确 | 真实 transport / 进程 |
| 服务集成 | 服务边界契约成立 | 用户可见状态 |
| Current fixture | 主链接线正确 | 真实宿主形态 |
| **Gate A** | 用户可见状态的**投影**正确 | 真实宿主进程链路 |
| **Gate B** | 真实 Electron/stdio/PTY + 真实输入的端到端主链 | 线上环境 |

配套硬规则：

- **Gate A 不能替代 Gate B**；低级证据不得冒充高级证据，引用时必须写明等级；
- 测试从 public 入口进入（协议/命令外沿），不直接调私有 handler；
- 等待业务事件，不用固定 sleep；
- 测试失败必须"回写"：修产品、修测试、补守卫，三选一；
- 未跑的命令必须写：未跑 / 原因 / 风险 / 后续触发条件。

还有一个**改动类型 → 最低验证矩阵**：任意改动 → verify:local；协议改动 → test:contracts；主链改动 → Gate B 冒烟。让"要跑什么"变成查表而不是临场发挥。

**模板对应**：`internal/aiprompts/quality-workflow.md`。

**新项目怎么用**：把 Gate A/B 翻译成你的项目语境——Gate A 是"投影/读模型层验证"（比如 API 响应快照），Gate B 是"真实进程 + 真实 transport + 真实输入"（比如真实启动应用点一遍主流程）。关键是保留"低级证据不得冒充高级证据"这条红线。

**何时可裁剪**：无 GUI 的项目可以把 Gate A/B 退化成 integration / e2e 两级，但等级语义必须保留。

### 3.6 并行协作协议

**是什么**：多个 Agent（或多个人 + Agent）同时改一个仓库时，靠"声明写集"而不是靠运气避免互踩。

**Lime 怎么做的**（parallel-agent-collaboration.md）：

- **默认不启用**——单 Agent 时直接干活，协议只在三种条件之一成立时触发：用户明说有其他 Agent 在跑、工作树有大量无关脏改动、任务要求进共享认领队列。这一点很重要：协议本身不能变成日常开销；
- 启动协议：确认主线 → **只读盘点**（`git status --short -- <scope>`，不要先改文件）→ 三段式声明写集（我认领 / 我只读 / 我不碰）；
- **写集要窄**："优先按垂直切片认领最少文件；不能用'整个 src/features/plugin'替代真实写集"；
- **脏热区避让**：目标文件已脏不夹写；必须同改时先汇报补丁点等合并窗口；发现意外变化立即停下，**不要用 checkout/reset/stash 抹平**；
- **执行计划避让**：主计划出现并行分歧时不夹写主计划，改写独立 `<topic>-progress.md`；
- **收尾五项汇报**：认领写集 / 避让写集 / 验证口径 / 下一刀归属 / 治理分类。

**模板对应**：`internal/aiprompts/parallel-agent-collaboration.md`。

**新项目怎么用**：几乎可以原样照搬，只需要补一份"本项目共享热区清单"（协议定义、公共 gateway、门禁脚本这类大家都想动的文件）。

**何时可裁剪**：几乎不需要裁剪——协议默认关闭，启用条件天然限制了成本。

### 3.7 架构确认制度

**是什么**：重大架构变更必须在同一个变更集里更新架构图，并由责任开发者署名确认。

**Lime 怎么做的**：

- 重大变更的定义是枚举的：新增/删除顶层目录或 owner、改变业务主链、改变协议边界、引入新的持久化或 transport、复活任何 dead 条目；
- 确认块是固定格式的文本，粘贴在执行计划和 PR 描述里：

```
Architecture impact: major
架构图已更新：<章节号与链接>
Responsible developer confirmation: <姓名/代号>, <日期>
确认内容：<一段话说明改动、替代方案与回滚策略>
```

- 规则的后半句是牙齿："未确认不得标记完成或进入 release evidence"；
- architecture.md 因此是一个**活的**文档：稳定骨架（裁决顺序、目录地图、依赖方向）+ 滚动追加的 Owner 章节（每个跨层能力一章，重大决策随章节落确认块）。

**模板对应**：`internal/aiprompts/architecture.md` 第 5 节。

**新项目怎么用**：直接使用确认块模板；Agent 侧的对应行为是"改完架构必须在同一 PR 里改文档，否则不算完成"。

**何时可裁剪**：不需要裁剪，成本几乎为零，缺了它的后果最大（架构图三个月就烂掉）。

## 4. 在新项目落地的七步

按收益/成本排序，每一步都可以独立停住：

| 步骤 | 做什么 | 为什么在这个位置 |
| --- | --- | --- |
| 1 | 复制 `AGENTS.md`，逐条审阅并适配（搜索 `适配标记`） | 半小时拿到全部约束的骨架 |
| 2 | 接入 `scripts/verify-local.mjs` + 行数棘轮，跑一次 `--update` 生成基线 | 第一条真正"会咬人"的规则 |
| 3 | 建 `internal/exec-plans/`，下一个长任务就用 `task-plan.md` 模板 | 让执行记录开始沉淀进仓库 |
| 4 | 写 `architecture.md`（裁决顺序 + 目录地图 + 业务主链三节起步） | 有了它，Agent 才能自己回答"改哪儿" |
| 5 | 补 governance.md 四态 + quality-workflow.md 证据分级 | 出现新旧并存或证据争议时立即需要 |
| 6 | 接入契约检查、legacy 守卫等进阶门禁 | 按需增长，每条挂进 verify-local 任务表 |
| 7 | 团队/Agent 评审一轮：删掉没人执行的规则，给留下的规则补守卫 | 规则的有效性靠 pruning 维持 |

判断落地是否成功的标志：**新 Agent 进仓库后，不看任何聊天记录，只读仓库内文件，就能正确回答——规则在哪、改哪个目录、跑什么命令、什么算完成。**

## 5. 与 AI Agent 的日常操作流

### 开工（新任务）

1. 判断是否长任务 → 是则在 exec-plans 建计划（目标 + 写集 + 退出条件）；
2. 判断是否并行场景 → 是则先 `git status` 盘点、声明三段写集；
3. 指示 Agent 先读：AGENTS.md → 相关领域文档 → 相关计划，**然后才动手**。

可以直接对 Agent 说的话：

> 开始前先读 AGENTS.md 和 internal/aiprompts/architecture.md 的相关章节，声明你的写集（认领/只读/不碰），先建 internal/exec-plans/<topic>-plan.md 再动手。

### 每刀（一轮改动）

1. 改动范围必须落在计划的写集内，越界先改计划再改代码；
2. 每刀收口：跑最低验证（查表）→ 在计划进度记录追加一刀（改动/验证/完成度/下一刀）；
3. 遇到脏热区或意外变化：停，上报，不抹平。

> 本刀完成前跑 `npm run verify:local`，把结果追加到计划的进度记录，写明完成度和下一刀。不要把单测通过说成 Gate B 通过。

### 收尾（任务完成）

1. 在计划"当前结论"写治理四分类、验证结果、未验证原因；
2. 完成度百分比——没有百分百就说百分之几；
3. Agent 最终汇报必须复述这五件事：改了什么、验证了什么（证据等级）、没验证什么（原因与风险）、四分类变化、下一刀。

> 收尾按 AGENTS.md 执行方式第 4 条汇报：current/compat/deprecated/dead 分类、验证结果、未验证原因、完成度百分比。

## 6. 常见误区与反模式

| 反模式 | 后果 | 正确姿势 |
| --- | --- | --- |
| 规则写了但没守卫 | 规则变成许愿，Agent 三天后开始违反 | 没有退出码的规则不要写进 AGENTS.md |
| 用 `--update` 走捷径 | 基线棘轮失效，门禁形同虚设 | `--update` 前问自己"我真的接受现状吗"，并在计划里留一句理由 |
| 为省 diff 新建 compat 层 | 双轨永生，current 永远收敛不了 | 直接替换 + 退役三件套 |
| 单测通过就宣布完成 | 上线才发现主链断了 | 查最低验证矩阵；引用证据必须写等级 |
| 写集声明"整个 src/features" | 写集失去避让意义 | 窄写集，垂直切片 |
| 出冲突就 checkout/reset | 抹平了别人的工作 | 停下上报，等合并窗口 |
| 架构变更不改架构图 | 文档三周腐烂，Agent 全靠猜 | 重大变更枚举清单 + 确认块，未确认不算完成 |
| 计划文件写成一次性日记 | 执行记录重新散落回聊天记录 | 每刀追加、收尾四分类、被替代就删除 |
| 门禁一刀切清历史欠账 | 团队被存量违规淹没，最后关掉门禁 | 基线棘轮：冻结现状，只许变好 |
| 把 AGENTS.md 写成百科全书 | Agent 上下文爆炸，关键规则被淹没 | 根文件 ≤ 2 页；细节下沉到领域文档 |

## 7. 术语表

| 术语 | 含义 | 出处 |
| --- | --- | --- |
| 主链 | 业务唯一主路径（Surface → 边界 → 核心 → 投影 → 持久化） | AGENTS.md 事实源 4 |
| owner | 某种能力唯一继续演进的实现/目录 | governance.md |
| current / compat / deprecated / dead | 能力生命周期四态 | governance.md |
| forbidden-to-restore | 退役对象的标准措辞，禁止任何形式恢复 | governance.md 退役三件套 |
| 写集 | 一轮改动认领要改的文件集合（配套：只读集、避让集） | parallel-agent-collaboration.md |
| 脏热区 | 已被并行进程改动的共享文件 | parallel-agent-collaboration.md |
| 一刀 | 一轮可验证的完整改动；计划进度以刀为单位追加 | exec-plans |
| 下一刀 | 主目标的下一个可执行阶段，每刀收尾必须写明 | exec-plans / AGENTS.md |
| 退出条件 | 阶段完成的可观察事实判据（不是"做完了"） | task-plan.md |
| 证据分级 | Unit → … → Gate A → Gate B → Live 的证据强度刻度 | quality-workflow.md |
| Gate A / Gate B | 投影级证据 / 真实进程端到端证据；A 不能替代 B | quality-workflow.md |
| 验证合同 | 主链改动开工前填写的必跑命令与证据承诺 | agent-verification-contract.md |
| 收尾四分类 | 收尾必须报告 current/compat/deprecated/dead 增删 | AGENTS.md 执行方式 4 |
| 完成度百分比 | 收尾必须量化；未验证部分不得计为完成 | AGENTS.md 执行方式 4 |
| 基线棘轮 | 冻结存量违规现状、只许改善不许恶化的门禁机制 | check-file-size-governance.mjs |
| 冻结基线 | scripts 等目录的结构快照，新增条目即违规 | check-scripts-baseline.mjs |
| verify:local | 默认本地门禁编排器，按改动路径增量选任务 | scripts/verify-local.mjs |
| 下一跳路由 | aiprompts/README 的"先读 X 再看 Y"两跳表 | aiprompts/README.md |
