# internal/prd — 需求

本目录是需求事实源：写清产品要做什么、不做什么、怎样算满足。读者是实现 lime-star 的编码 Agent；仓库所有者负责确认。边界与目录归属以 `../aiprompts/architecture.md` 为准；本页只定义需求层的用法。

## 一份需求由哪些文件组成

- 一份需求是一个全局文件加一个同名目录。全局文件放每次开工都要读的内容：状态、阅读规则、目标、主场景、成功标准、范围、术语、全局约束、文件地图。
- 同名目录下按能力一个文件。每个文件自包含：摘要、包含的需求编号、先读什么、需求、本能力的未决与决策。
- 能力之间只用编号和路径互相引用。一条需求只出现在一个文件里。
- 现有的例子：`agent-practice.md` 和 `agent-practice/`。

## 写作要求

1. 写对外可观察的行为：命令、终端输出、文件变化、会话记录。不写模块划分、文件路径选型和实现步骤，那些归 `../aiprompts/architecture.md` 和执行计划。
2. 全局文件开头写明状态（草稿或已确认）与确认人。未确认的需求不得被计划当成既定范围；状态为草稿时，依赖它的阶段不得开工。
3. 一条需求只写一个可观察的行为，带全局唯一的编号（R7.2），用"必须、应当、可以"标强度。陈述里只放一个"必须"；第二个行为另立一条。
4. 每条需求至少配一个场景（R7.2-S1），写成"给定、当、则"。场景要覆盖出错和边界，不只写正常路径。
5. 范围两头都写：做什么，以及明确不做什么并附理由。
6. 边界情况只写 Agent 否则会猜错的地方：默认值、拒绝路径、取消后发生什么。"边界"行只写补充说明；其中的行为要升成带场景的需求。
7. 做了默认选择就记一条决策：选了什么、为什么、落选的备选是什么。
8. 需要仓库所有者定的问题记为未决，写明推荐答案、备选和它阻塞的阶段与需求；未决超过 5 个先答疑再继续写。
9. 需求由哪个阶段交付写路线图，不写在这里；路线图的每个阶段列出交付的需求编号和要读的需求文件。
10. 单个文件超过约 300 行按能力再拆，少于 30 行并回上一级。跨文件引用同目录写文件名，跨目录写相对路径。
11. 被替代且没有外部依赖的需求直接删除，历史归 Git。需求编号不复用。

## 写完之后自检

出草稿的 Agent 先自检再交给仓库所有者，最多三轮，把结果写进执行计划：

- 每个 `### R` 需求有一个"陈述"和至少一个带"给定、当、则"的场景；需求编号和场景编号没有重复。
- 没有占位内容，没有"待定"。
- 路线图里引用的需求编号都存在；每条需求都映射到了阶段，MVP 内的需求在 P0 到 P4 交付。
- 需求文件里没有内部模块名。
- 没有模糊词（简单、快速、友好、尽量）；有数字的地方给了具体值。
- 每条决策都写了落选的备选；未决不超过 5 个。
